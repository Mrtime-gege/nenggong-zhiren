# 本机安全扫描与真实浏览器复测

日期：2026-10-26（Asia/Shanghai）
范围：本机 `7355`（当前实例，只做只读扫描）和隔离实例 `7361`（同一代码、临时数据）。
约束：不扫描网段、不做破坏性利用、不修改目标文件、不种植后门；如果凭证被猜中，只验证
登录成功即停止。

## 1. 工具

工具从本机 Kali 软件源下载后解包到临时目录运行，没有系统级安装、没有 sudo：

| 工具 | 版本 | 用途 |
| --- | --- | --- |
| Nmap | 7.99 | 端口/服务发现 |
| ffuf | 2.1.0 | 路径枚举 |
| Gobuster | 3.8.2 | 目录枚举 |
| Nikto | 2.6.1 | Web 配置/常见路径扫描 |
| Nuclei | 3.11.1 | 自定义无破坏模板 |
| Python requests | 2.34.2 | 登录限速/SQLi/路径/方法测试 |

说明：Hydra 包在本机缺少可选协议库，未直接运行；登录暴力测试用 Python requests 完成。
目标没有 SQL 后端，SQLmap 不适用；SQLi 用人工 payload 验证。Nuclei 使用只读自定义模板。

## 2. 真实浏览器复测

使用真实 Chromium（非 curl）对当前实例重复执行：

1. 同源表单登录 → 跳转 `/console`，右上角显示管理员；
2. 刷新页面 → 会话保持；
3. 退出 → 回到 `/login`；
4. 错误密码（不存在的测试用户）→ 页面内显示“用户名或密码错误”，不是 JSON 错误；
5. 再次登录 → 成功；
6. 发起工具调用票据 → 浏览器认领、填写 `{"city":"北京"}`、完成 → 调用方 200、
   `finish_reason=tool_calls`；
7. JSON 模式 → 先提交非法 JSON 得到 400，票据保留；改成 `{"ok":true}` 后调用方 200；
8. 在浏览器里直接发无 CSRF 的写请求 → 403；正常 UI 请求带 CSRF 成功；
9. 右上角「用户管理」→ 添加临时坐席、重置密码、删除；管理员会话不会被文件热重载踢掉。

另外，`npm test` 的 24 项自动化用例全部通过，包含 Web 用户管理、角色校验和会话保留。

## 3. 扫描结果

### 3.1 端口

Nmap 仅发现：

```text
7355/tcp open
7361/tcp open
```

没有发现额外开放端口；服务没有 `Server`/`X-Powered-By` 版本泄露。

### 3.2 路径枚举

ffuf + Gobuster 使用小规模路径字典（登录、控制台、API、配置、备份、`.env`、`.git`、
`users.json` 等），只命中预期资源：

- `/login`、`/login.css`、`/login.js`、`/healthz`：公开；
- `/console`：未登录 302 到登录页；
- `/v1/models`、`/v1/chat/completions`、`/op/api/*`：401/405；
- `/users.json`、`/.env`、`/.git/HEAD`、`/data/users.json`：**404**。

### 3.3 Nikto

第一次扫描发现一个真实的健壮性问题：

```text
GET //////////////////...  → 500
```

原因是 malformed request URL 让 `new URL()` 抛异常，服务端返回 500。已修复为 400
`invalid_url`，并增加回归测试；第二次扫描不再出现 500。

剩余报告：

- `strict-transport-security` 缺失：当前是 HTTP 实例，这是已知设计限制；启用 TLS 后自动
  发送 HSTS；
- `x-request-id` 被标为 uncommon header：信息性提示，不是漏洞；
- 没有发现目录列表、备份、`.git`、`.env`、用户文件暴露。

### 3.4 Nuclei

使用三个只读自定义模板：

- 登录页是否缺少 CSP / X-Frame-Options / nosniff；
- `.env` / `.git/HEAD` / `data/users.json` 是否可读。

修正模板的大小写匹配后，结果为 **0 条命中**：安全头存在，敏感文件 404。

### 3.5 登录暴力破解与限速

隔离实例上连续提交 5 次错误密码：

```text
401, 401, 401, 401, 401, 429
```

第 6 次被限速拦截，带 `Retry-After`。之后只重启隔离实例、使用已知测试密码验证登录
返回 303，**没有继续利用，也没有读取/导出任何数据**。

### 3.6 注入、方法和路径

| 测试 | 结果 |
| --- | --- |
| SQLi 登录 payload | 401，无 500 |
| XSS payload 作为用户名 | 401，页面不回显 |
| `..%2f` / `%2e%2e` / `..%5c` 路径穿越 | 404 |
| `TRACE` / `PUT` / `PATCH` / `DELETE /` | 404/405 |
| `Host: evil.example` | 421 |
| `/v1` CORS preflight | 204 + `Access-Control-Allow-Origin` |
| `users.json` 直接访问 | 404 |
| 未认证 `/op/api/users` | 401 |
| 重复认领 | 409 |
| 缺 CSRF 写请求 | 403 |

## 4. 结论

本轮**未发现可远程直接获取管理员权限、读取用户文件或读取票据内容的高危/严重问题**；
发现并修复了一个 malformed URL 导致 500 的健壮性问题。登录限速、Host/Origin、CSRF、
路径白名单和敏感文件隔离均按预期工作。

这不是“绝对安全”的证明：没有做公网外部扫描、压力测试、供应链审计、浏览器 0day 测试，
也没有攻击 TLS 层（当前实例是 HTTP）。最大的残余风险仍是 **局域网 HTTP 明文登录**；
正式发布前应启用项目内置 TLS 或反代 TLS，并轮换测试用调用方 key。
